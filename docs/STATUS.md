## สรุปสั้นที่สุด

ระบบ **สร้างเสร็จและทดสอบแล้ว** แต่ **ยังเปิดใช้จริงไม่ได้** เพราะติดที่ข้อมูล ไม่ใช่ที่โค้ด

| | สถานะ |
|---|---|
| โค้ดระบบ (POS, ฐานข้อมูล, ไปป์ไลน์ข้อมูล) | ✅ เสร็จ ทดสอบผ่าน |
| ข้อมูลสินค้าและราคา | ⚠️ ยังไม่พร้อม — ดูหัวข้อ "ติดอะไรอยู่" |
| การ deploy ขึ้นใช้งานจริง | ⛔ ยังไม่ได้ทำ — ต้องใช้บัญชี Google ของร้าน |

**สิ่งที่ต้องทำก่อนใช้งานได้จริง เรียงตามลำดับ:** ตั้งค่า Google Sheet + Apps Script →
เดินยิงบาร์โค้ด 139 รายการ → เก็บราคา Makro 130 รายการ → ตรวจนับสต็อกจริง

## ทำอะไรไปแล้วบ้าง

### 1. ระบบ POS ใช้งานได้ทั้ง iPhone และ Windows (PWA)

เป็นเว็บแอปเดียวที่ติดตั้งเป็นแอปได้ทั้งสองแพลตฟอร์ม ไม่ต้องผ่าน App Store ไม่ต้องมี
Apple Developer account หน้าจอที่มี:

| หน้า | ทำอะไร |
|---|---|
| เข้าสู่ระบบ | ล็อกอินด้วย PIN (เก็บเป็น SHA-256 ไม่ใช่ตัวเลขเปล่า) |
| ขายของ | ค้นหา/ยิงบาร์โค้ด, ตะกร้า, ส่วนลด, คิดราคาส่งอัตโนมัติ, **พิมพ์ใบเสร็จ** |
| สต็อก | ดูคงเหลือ, ไฮไลต์สินค้าใกล้หมด, **แสดงต้นทุนและกำไรต่อรายการ** |
| รายงาน | ยอดขาย **กำไรขั้นต้น** สินค้าขายดี เตือนสินค้าขายต่ำกว่าทุน และ **ยกเลิกบิล** |
| เก็บบาร์โค้ด | เดินยิงบาร์โค้ดทั้งร้าน พร้อมแถบความคืบหน้า |
| ตรวจนับ | กรอกจำนวนที่นับได้จริง ระบบคำนวณส่วนต่างและบันทึกที่มาให้ |
| สั่งซื้อ/รับของ | รายการที่ต้องซื้อ + ประมาณการค่าใช้จ่าย และบันทึกของที่ซื้อกลับมา |

**ขายตอนเน็ตหลุดได้** บิลถูกเก็บใน IndexedDB แล้ว sync อัตโนมัติเมื่อเน็ตกลับมา
มีกลไกกันบันทึกซ้ำด้วย `clientSaleId` เผื่อยิงซ้ำระหว่าง sync
— **ทดสอบเส้นทางนี้จริงแล้ว** (ตัดเน็ต → ขาย → บิลเข้าคิว → ต่อเน็ต → คิวว่าง)

### 2. ต่อยอดฐานข้อมูล PostgreSQL Phase 1 ของคุณ

ไม่ได้สร้างฐานข้อมูลใหม่ซ้อน แต่เขียน migration ต่อจาก `006` ที่คุณมีอยู่:

- `sql/007` เพิ่มคอลัมน์ที่ POS ต้องใช้ (ต้นทุน, ราคาปลีก/ส่ง, จุดสั่งซื้อ, จำนวนต่อแพ็ค)
  และตาราง `vendor_price_research` ที่แยกบทบาทผู้ขาย
- `sql/008` นำเข้าข้อมูลจาก CSV แบบรันซ้ำได้ไม่เกิดข้อมูลซ้ำ
- `sql/009` เพิ่มระดับ `template_sample` และเก็บรหัส SKU เดิม

ทุกตัวรันซ้ำได้ปลอดภัย และ **ทดสอบบน PostgreSQL จริงแล้ว** ผ่าน 6 ข้อ รวมถึงข้อที่ยืนยันว่า
การคำนวณกำไรฝั่ง SQL กับฝั่ง Python ให้คำตอบตรงกัน (`./tests/run_sql_tests.sh`)

### 2.1 การทดสอบทั้งหมดที่มี

### 3. ไปป์ไลน์ข้อมูลอัตโนมัติ

```
Google Sheet "สินไทยพาณิชย์"  ← คุณแก้ที่นี่ที่เดียว
        │  scripts/import_from_sheet.py
        ▼
   data/*.csv (อยู่ใน git ตรวจ diff ได้ว่าอะไรเปลี่ยน)
        │  scripts/build_catalog.py
        ├──► PostgreSQL          ← ฐานข้อมูลหลัก
        └──► แผ่น Products       ← ที่ POS ใช้จริง
```

ไม่ต้องพิมพ์ข้อมูลซ้ำอีกเลย และ **ต้นทุน/กำไรไม่ถูกพิมพ์เก็บไว้** แต่คำนวณจากราคาซัพพลายเออร์ทุกครั้ง
จึงไม่มีทางค้างอยู่กับราคาเก่าโดยไม่มีใครรู้

### 4. แยกบทบาทผู้ขาย — จุดที่เปลี่ยนเกมมากที่สุด

ชีตเดิมจัด **Makro, Lotus, BigC เป็น "vendor" เหมือนกันหมด** แต่จริงๆ คนละหน้าที่:

- **Makro = แหล่งซื้อ** → ราคานี้คือ *ต้นทุน* ของร้าน
- **Lotus / BigC = คู่แข่ง** → ราคานี้คือ *เพดาน* ที่ตั้งราคาขายได้

ตราบใดที่ไม่แยกสองอย่างนี้ จะคำนวณกำไรไม่ได้เลย พอแยกแล้วปัญหาจริงก็โผล่ขึ้นมาทันที

### 6. เครื่องมือสองตัวที่สร้างให้เพื่อปลดล็อกงานที่เหลือ

- **หน้าเก็บบาร์โค้ดในแอป** — เดินยิงทั้งร้านได้เลย ตรวจหลักตรวจสอบ GS1 ก่อนบันทึกทุกครั้ง
  รองรับเครื่องยิง USB/บลูทูธ (ทำตัวเหมือนคีย์บอร์ด) และกล้องมือถือบนเครื่องที่รองรับ
- **ใบงานเก็บราคา Makro** (`scripts/make_price_worklist.py`) — พิมพ์พกไป Makro ได้
  จัดลำดับให้แล้วว่าควรเก็บตัวไหนก่อน โดยดูจากหลักฐานในข้อมูลเอง:
  8 รายการด่วนที่สุด (แบรนด์ที่พบว่าขาดทุนแล้ว), 53 รายการที่ตั้งราคาเหมาเท่ากัน, ที่เหลือ 69

## ติดอะไรอยู่

### ⛔ ตัวบล็อกที่ 1 — บาร์โค้ดขาด 139 จาก 141 รายการ

**ทำไมถึงติด:** ชีตมีบาร์โค้ดจริงแค่ 2 รายการ ที่เหลือยิงขายที่เคาน์เตอร์ไม่ได้

**ทำไมผมแก้ให้เองไม่ได้:** บาร์โค้ดต้องอ่านจากตัวสินค้าจริงเท่านั้น ถ้าไปหาจากอินเทอร์เน็ต
แล้วกรอกเอง มีโอกาสได้ของผิดรุ่นผิดขนาด ซึ่ง**อันตรายกว่าไม่มีบาร์โค้ดเลย** เพราะยิงแล้วจะได้
สินค้าผิดตัว ตัดสต็อกผิด และคิดเงินผิดราคา โดยไม่มีใครสังเกต

**ทางออกที่เตรียมไว้แล้ว:** เปิดแอป → แท็บ "เก็บบาร์โค้ด" → เดินยิงทีละตัว ระบบมีแถบ
ความคืบหน้าบอกว่าเหลืออีกกี่รายการ

> สินค้าแบ่งขายที่ไม่มีบาร์โค้ดโรงงาน กดปุ่ม **"ออกรหัสภายในร้าน"** ในหน้าเดียวกันได้เลย
> ระบบออกรหัสขึ้นต้นด้วยเลข `2` ให้ (GS1 สงวนช่วงนี้ไว้ให้ร้านใช้เองโดยเฉพาะ จึงไม่ชนกับ
> บาร์โค้ดสินค้าจริง) แล้วต้อง **พิมพ์สติกเกอร์ติดที่ตัวสินค้า** ด้วย ไม่งั้นยิงขายไม่ได้

### ⛔ ตัวบล็อกที่ 2 — ไม่รู้ต้นทุน 130 จาก 141 รายการ

**ทำไมถึงติด:** มีราคา Makro แค่ 11 รายการ ที่เหลือคำนวณกำไรไม่ได้เลย แปลว่าตอนนี้
**92% ของสินค้าในร้านยังไม่รู้ว่าขายแล้วได้กำไรหรือขาดทุน**

ราคาที่มีในชีตส่วนใหญ่เป็นของ BigC (26 แถว) และ Lotus (17 แถว) ซึ่งเป็นคู่แข่ง ไม่ใช่แหล่งซื้อ
ส่วนอีก 70 แถวเป็นแถวตั้งไว้รอกรอก (`Pending Vendor Price`) ยังไม่มีตัวเลข

**ทำไมผมแก้ให้เองไม่ได้:** ราคา Makro ต้องดูจากป้ายจริงหรือหน้าสินค้าจริง และต้องเป็น
**ขนาดบรรจุเดียวกัน** เท่านั้น การเดาจะทำให้ตัวเลขกำไรผิดทั้งระบบ

**ทางออกที่เตรียมไว้แล้ว:** `python3 scripts/make_price_worklist.py` → พิมพ์
`build/makro_worklist.html` พกไป → กรอกราคา → วางกลับเข้าชีต `Reference`

### ⚠️ ตัวบล็อกที่ 3 — สต็อกยังเป็น 0 ทั้งหมด

ยอดคงเหลือตั้งต้นเป็น 0 ทุกรายการ ยังไม่ใช่ของจริง ต้องตรวจนับก่อนเปิดใช้
ไม่งั้นระบบจะไม่ยอมให้ขาย (มีการเช็กสต็อกก่อนตัด)

**ทางออกที่เตรียมไว้แล้ว:** เปิดแอป → แท็บ "ตรวจนับ" → กรอกจำนวนที่นับได้จริงทีละรายการ
มีตัวเลือก "ซ่อนที่นับแล้ว" เพื่อไล่นับให้ครบโดยไม่หลงรายการ

### ⚠️ ต้องยืนยัน: รหัส SKU ที่ระบบออกให้ 56 รายการ

สินค้า 56 รายการในชีตไม่มีรหัส SKU เลย ระบบออกให้เป็น `SKU0086`–`SKU0141` โดยเรียงตาม
(แบรนด์, ชื่อ) เพื่อให้รันซ้ำได้รหัสเดิมเสมอ **แต่ยังต้องให้คุณยืนยันก่อนพิมพ์ป้ายหรือใช้ถาวร**
สินค้ากลุ่มนี้ยังไม่มี Category/Subcategory ด้วย

### ⚠️ ต้องตรวจซ้ำ: ข้อมูลที่ความน่าเชื่อถือต่ำ

- `SKU0006` / `SKU0007` เป็นคนละขนาด แต่ได้ราคา Makro 47 และ BigC 62 เท่ากันเป๊ะ
  เพราะดึงจากหน้า search ไม่ใช่หน้าสินค้าตรงรุ่น
- `pack_qty` ของสินค้าที่ชื่อไม่ระบุจำนวนต่อแพ็ค ระบบตั้งเป็น 1 และติดธง
  `pack_qty_not_in_name` ไว้ — ถ้าจริงๆ เป็นแพ็ค ตัวเลขกำไรจะผิด

### ℹ️ ยังไม่ได้ deploy

โค้ดพร้อม deploy แล้ว (มี GitHub Actions รอไว้) แต่ผมทำให้ไม่ได้เพราะต้องใช้
**บัญชี Google ของร้าน** สร้าง Apps Script และ **สิทธิ์ตั้งค่า repo** ขั้นตอนอยู่ใน
[`../README.md`](../README.md) และ [`../apps-script/README.md`](../apps-script/README.md)

### ℹ️ จำนวนสินค้ายังไม่ถึง 350

คุณแจ้งว่าร้านมีสินค้ากว่า 350 รายการ ชีตปัจจุบันมี 141 ระบบรองรับ 350+ อยู่แล้ว
รอเพียงข้อมูลที่เหลือเติมเข้าชีตแล้วรัน import ใหม่

> ผม **ไม่ปั้นสินค้าปลอมอีก 200 กว่ารายการมาเติมให้ครบ** เพราะข้อมูลแต่งจะปนกับของจริง
> จนแยกไม่ออก แล้วกลายเป็นฐานของการตัดสินใจเรื่องราคาและการสั่งซื้อที่ผิดพลาด

## สิ่งที่ตัดสินใจเปลี่ยนระหว่างทาง (และเหตุผล)

### เปลี่ยนฐานข้อมูลหลักจาก Google Sheets เป็น PostgreSQL
ตอนถามรอบแรกคุณเลือก "Google Sheets เป็นฐานข้อมูลหลัก" แต่ผมยังไม่รู้ว่าคุณมี Phase 1
เป็น PostgreSQL อยู่แล้ว พอเห็นไฟล์ที่ส่งมาจึงเปลี่ยน เพราะการมีฐานข้อมูลหลักสองที่
จะทำให้ข้อมูลค่อยๆ เพี้ยนออกจากกันจนไม่รู้ว่าฝั่งไหนถูก

### แก้ข้อสรุปที่รายงานผิดไปก่อนหน้า
เคยรายงานว่า `SKU0001` และ `SKU0002` ขายต่ำกว่าทุน — **ผิด** เพราะราคานั้นคือค่าตัวอย่าง
ที่ติดมากับเทมเพลต (ชีตเขียนกำกับไว้เองว่า "Original sample data retained from template")
แต่กลับติดสถานะเป็น `Verified` ตอนนี้ระบบตัดออกแล้ว

> **บทเรียนที่ควรจำ:** สถานะ `Verified` ในชีตเชื่อไม่ได้เสมอไป ต้องอ่านหมายเหตุประกอบ

### แก้บั๊กในตรรกะวิเคราะห์ของผมเอง
ระบบเคยแนะนำว่า "คู่แข่งขายถูกกว่าทุน ต้องหาแหล่งซื้อใหม่" สำหรับ `SKU0020` — คำแนะนำนั้นผิด
เพราะ BigC 42 บาทคือเค้ก **144 ก.** ส่วนของเราคือ 17 ก. x12 = **204 ก.** คิดต่อกรัมแล้ว
Makro ถูกกว่าด้วยซ้ำ ตอนนี้ใช้เฉพาะราคาที่ยืนยันว่าตรงรุ่นตรงขนาดมาตั้งเพดาน

---

## คำสั่งที่ใช้บ่อย

```bash
# นำเข้าข้อมูลใหม่จากชีต (ดาวน์โหลด .xlsx ทับ data/source/ ก่อน)
python3 scripts/import_from_sheet.py

# ดูรายงานสุขภาพราคา — ออก exit code 1 ถ้ามีสินค้าขายต่ำกว่าทุน
python3 scripts/build_catalog.py

# สร้างใบงานเก็บราคา Makro
python3 scripts/make_price_worklist.py

# ทดสอบ (ต้องมี PostgreSQL ในเครื่อง)
./tests/run_sql_tests.sh
cd web && npm test
```
